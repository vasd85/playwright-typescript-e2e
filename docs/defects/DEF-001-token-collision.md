# DEF-001. Одновременные регистрации получают один и тот же токен

| | |
| --- | --- |
| **Идентификатор** | DEF-001 |
| **Компонент** | демо-бэкенд Conduit, авторизация |
| **Среда** | `https://api.realworld.show/api`; бэкенд `realworld_dummy_server.py` репозитория `c4ffein/realworld-demo-deploy`, коммит `ba2b78f6` |
| **Обнаружен** | 2026-09-03, на прототипе авторизации — до первого коммита этого репозитория, поэтому в его истории следов той работы нет |
| **Воспроизведён** | 2026-09-09, вывод ниже |
| **Серьёзность** | высокая |
| **Статус** | открыт, обход применён в каркасе тестов |

## Описание

Две и более регистрации, попавшие в одно и то же значение целой секунды,
получают **байт в байт одинаковый токен**. Стенд привязывает этот токен к сессии
того, кто зарегистрировался последним, поэтому остальные аккаунты молча начинают
работать под чужой личностью. Никакой ошибки при этом нет: все регистрации
возвращают 201, а `GET /user` отвечает 200 — просто другим пользователем.

## Влияние

Дефект ломает параллельный прогон автотестов, если тот регистрирует пользователей
одновременно — а это обычный способ дать воркерам независимые учётные записи.
Наблюдалось при разработке этого каркаса: воркеры получали общий токен, и тест
падал на проверке шапки, потому что в браузере был пользователь другого воркера.
*Артефакт того прогона в репозиторий не входит, поэтому здесь это иллюстрация, а
не доказательство; доказательство дефекта — вывод скрипта ниже.* Диагностируется
тяжело: симптом не похож на причину, падает не авторизация, а произвольная
проверка ниже по сценарию с сообщением вида «элемент не найден».

*Следствие, не измерено:* уборка данных идёт от имени токена, поэтому при
коллизии один воркер удаляет статьи другого.

**Почему этот класс дефектов критичен там, где идут платежи.** Оценка
серьёзности выше дана для демонстрационного стенда. Но сам класс —
предсказуемый идентификатор сессии, выведенный из данных, совпадающих у разных
пользователей, — в платёжном продукте означает доступ к чужой сессии, то есть к
чужим данным и операциям. Это нарушение изоляции пользователей, а не дефект
удобства: частота проявления на приоритет не влияет.

## Шаги воспроизведения

1. Отправить четыре запроса `POST /users` параллельно, так чтобы они пришлись на
   одну целую секунду по часам сервера.
2. Дождаться ответов. Все четыре возвращают 201 и токен.
3. Дождаться, пока секунда регистрации закончится по часам стенда: секунда
   берётся из заголовка `Date` ответа, ждать нужно до `секунда + 2`. Раньше
   сверять бесполезно — пока эта секунда идёт, привязку может перехватить
   следующая регистрация.
4. Для каждого выданного токена выполнить `GET /user` с заголовком
   `Authorization: Token <токен>`.
5. Сравнить имя из ответа с именем, под которым регистрировались.

Скрипт, делающий ровно это, лежит рядом. Он не требует ни установки зависимостей,
ни запуска тестов — только Node 20 или новее (использует встроенный `fetch` и
`parseArgs`):

```bash
node docs/defects/def-001-repro.mjs
```

Он выполняет два замера: четыре параллельные регистрации и четыре с паузой в
секунду. Необязательные флаги: `--api <адрес>` для другого стенда и `--n <2..4>`
для числа регистраций в замере (потолок 4 — стенд публичный и общий). Коды
выхода:

| Код | Значение |
| --- | --- |
| 0 | все личности сошлись, коллизия не воспроизвелась |
| 1 | **дефект воспроизведён** — хотя бы один токен резолвится в чужого пользователя |
| 2 | замер не состоялся: стенд ответил не 201 на регистрацию или не 200 на `GET /user`, не прислал разбираемый `Date`, не ответил вовсе, либо аргументы запуска неверны |

Код 1 означает найденный дефект, а не поломку скрипта. Токены в выводе
маскированы.

## Фактический результат

Прогон 2026-09-09, код выхода 1:

```
stand: https://api.realworld.show/api

burst: 4 registration(s) in parallel — the defect
POST /users -> 201 username=def00117889075492fd4n0 token=token_d978…0ac5 whoami=def00117889075492fd4n1 MISMATCH
POST /users -> 201 username=def00117889075492fd4n1 token=token_d978…0ac5 whoami=def00117889075492fd4n1 OK
POST /users -> 201 username=def00117889075492fd4n2 token=token_d978…0ac5 whoami=def00117889075492fd4n1 MISMATCH
POST /users -> 201 username=def00117889075492fd4n3 token=token_d978…0ac5 whoami=def00117889075492fd4n1 MISMATCH
unique tokens: 1 of 4
```

Четыре разных аккаунта получили один токен, и он принадлежит второму из них —
три из четырёх работают под чужой личностью.

Исход коллизии непредсказуем: побеждает привязка, выполнившаяся последней, а
порядок завершения параллельных запросов не задан. Число совпавших токенов тоже
плавает: залп, пришедшийся на границу секунды, частично уедет в следующую и
получит там собственные токены. Предсказуема сама коллизия, а не её исход и не
её масштаб.

## Ожидаемый результат

Каждая регистрация получает собственный токен, и каждый токен резолвится в того
пользователя, которому выдан. Именно это даёт второй замер того же прогона, где
регистрации разведены на секунду:

```
spread: 4 registration(s) 1s apart — the workaround
POST /users -> 201 username=def00117889075523e1fn0 token=token_08f2…d835 whoami=def00117889075523e1fn0 OK
POST /users -> 201 username=def00117889075523e1fn1 token=token_3c3b…7333 whoami=def00117889075523e1fn1 OK
POST /users -> 201 username=def00117889075523e1fn2 token=token_20d0…b270 whoami=def00117889075523e1fn2 OK
POST /users -> 201 username=def00117889075523e1fn3 token=token_a4db…b28f whoami=def00117889075523e1fn3 OK
unique tokens: 4 of 4
```

Во втором замере тоже возможен `MISMATCH` — стенд общий, и в ту же секунду может
зарегистрироваться кто-то посторонний. Это не опровергает обход, а показывает ту
же причину с внешним участником.

## Анализ причины

*Статус источника: по исходникам, не измерено.* Файл `realworld_dummy_server.py`,
коммит `ba2b78f6`.

Токен — чистая функция от идентификатора пользователя и целой секунды, без
случайной части. Функция `generate_token` занимает строки 1378–1381, считает её
тело:

```python
payload = f"{user_id}:{int(time.time())}"
return f"token_{hashlib.sha256(payload.encode()).hexdigest()[:32]}"
```

Оба слагаемых у независимых регистраций совпадают. Секунда — потому что запросы
пришли одновременно. Идентификатор — потому что счётчик объектов раздаёт номера
по порядку внутри сессии (строка 414), а свежая сессия всегда начинается с
четырёх демонстрационных пользователей, так что первый зарегистрированный в ней
получает один и тот же `id`.

Дальше обработчик регистрации привязывает выданный токен к сессии запроса
(строка 1560), а `bind_jwt_to_session_id` перед этим удаляет все прежние
привязки того же токена (строки 947–964, удаление на строке 956). Побеждает
последняя регистрация — её сессия и станет владельцем общего токена.

Отсюда же следует, что **дефект не ограничен одним клиентом**: адрес источника в
формулу токена не входит — `generate_token` его вообще не принимает. Любая
анонимная регистрация постороннего клиента, попавшая в ту же секунду, получит тот
же токен и перепривяжет его к своей сессии. Разводить по времени собственные
запросы поэтому недостаточно. *(Такой случай наблюдался при разработке фикстуры:
в браузере оказался пользователь, которого этот прогон не создавал. Артефакт того
прогона в репозиторий не входит, поэтому здесь он приведён как иллюстрация к
разбору исходников, а не как доказательство.)*

## Обход, применённый в каркасе

Три меры. Общая логика регистрации со сверкой лежит в
`src/auth/worker-session.ts`, а порядок регистраций задают её вызывающие.

**Первая — убрать одновременность.** Регистрации воркеров вынесены из времени
тестов в setup-проект: `tests/setup/worker-sessions.setup.ts` проходит слоты
циклом и регистрирует их один за другим, до того как стартует хоть один
браузерный тест. При четырёх воркерах это последовательный пролог примерно в
восемь секунд.

**Вторая — развести по секундам тех, кто всё же регистрируется во время
тестов.** Прогон без setup-проекта (например, демонстрационный запуск с
`--no-deps`) идёт запасным путём через фикстуру `src/fixtures/auth.fixture.ts`,
и там регистрация слота ждёт секунды, остаток которой от деления на число
воркеров равен номеру слота (`staggerToSlotSecond`). Слоты гарантированно
попадают в разные секунды.

**Третья — не доверять коду 201, а спросить, кому принадлежит токен.** После
регистрации выполняется `GET /user`, и его ответ годен только тогда, когда
секунда регистрации закончилась **по часам стенда**: секунда берётся из заголовка
`Date` ответа на регистрацию, сверка ждёт `Date` не меньше этой секунды плюс две.
Одна секунда — чтобы секунда токена истекла; вторая — запас на случай, если
заголовок `Date` отстаёт от собственных часов сервера (предположение, взятое как
страховка, а не измеренное свойство стенда). После этой границы токен уже никем
не может быть сгенерирован заново, и привязка окончательна. Несовпадение —
повторная регистрация в новой секунде, до трёх попыток. Цена — около двух секунд
на слот, один раз за прогон: стартовая пауза 1,5 секунды плюс ожидание границы.

Первые две меры закрывают столкновения между участниками своего прогона. Против
чужой регистрации на общем стенде работает только третья: она превращает такой
случай в явное падение с понятным текстом вместо загадочного «элемент не найден».
Скрипт воспроизведения из этого документа сверяет личность по тому же правилу —
поэтому строки `OK` в его выводе означают именно устоявшуюся привязку.

## Чем дефект ловится в наборе тестов

- Тест `the header shows the worker user without the login form`
  (`tests/ui/auth/worker-session.spec.ts`) — шапка обязана показывать
  пользователя своего воркера.
- Сценарий регистрации (`tests/ui/auth/registration.spec.ts`) после входа
  открывает страницу настроек навигацией и сверяет её поля с именем и почтой.
  Шапку приложение рисует по ответу на сам вход, поэтому подмену личности она
  показать не обязана; отдельная проверка полей эту дыру закрывает.
- При исчерпании трёх попыток регистрация падает с текстом
  `token collision on the stand`, то есть причина названа прямо.

## Рекомендация владельцу стенда

Добавить в токен случайную часть, чтобы он перестал быть чистой функцией от
идентификатора и секунды. Это устраняет причину целиком; проверки на стороне
клиента остаются полезными, но перестают быть обязательными.
