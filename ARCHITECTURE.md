# Архитектура e2e-тестов для миграции CMS с AngularJS на Angular в Nx

Решение кейса: как организовать тесты и page objects, чтобы переход со старого фронтенда на новый не переписывал текст тест-кейсов, и как устроить жизненный цикл `playwright.config.ts`. Каркас в этом репозитории закреплён на `@playwright/test` 1.62.1; у фактов о стенде и об инструментах, взятых не из прогона, статус источника стоит рядом.

## 1. Управление изменениями в дизайне страниц

### 1.1 Абстракция тестов от реализации элементов

Предлагаемая раскладка проекта `apps/cms-e2e` в монорепозитории (не этот репозиторий):

```
apps/cms-e2e/
  tests/             сценарии на языке бизнеса, без локаторов
  pages/contract/    интерфейсы страниц и компонентов
  pages/legacy/      реализации для AngularJS
  pages/next/        реализации для Angular
  pages/components/  реализации, не зависящие от версии: локаторы только по реестру и ролям
  fixtures/          сборка: авторизация, API, фабрика страниц
  data/              builders тестовых данных
libs/test-ids/       реестр идентификаторов, общий для приложений и тестов
```

Тест знает только интерфейс: `await editor.publish(article)`, `await editor.expectError('title', "can't be blank")`. Локаторы живут в реализациях, а какая из них подставится, решает опция проекта `appVersion`: она объявлена через `test.extend` с `{ option: true, scope: 'worker' }` (по документации, <https://playwright.dev/docs/test-parameterize>) и задаётся в `use` каждого проекта конфига. Фабрика в фикстуре читает опцию и создаёт реализацию:

```ts
export interface EditorPage {
  open(): Promise<void>;
  publish(article: ArticleDraft): Promise<void>;
  expectError(field: 'title' | 'body', text: string): Promise<void>;
}

export const test = base.extend<{ editor: EditorPage }, { appVersion: AppVersion }>({
  appVersion: ['next', { option: true, scope: 'worker' }],
  editor: async ({ page, appVersion }, use) => {
    const Editor = PAGES[appVersion].editor;
    test.skip(!Editor, `No ${appVersion} implementation for EditorPage yet`);
    if (!Editor) throw new Error('unreachable');
    await use(new Editor(page));
  },
});
```

Совпадающие 80 % сценариев идут в проектах обеих версий без единой правки текста теста. Реализаций у страницы одна или две. Одна — когда обе версии находят элементы по реестру и ролям, и в карте `PAGES` под обеими версиями стоит один класс. Две — когда старая версия осталась на классах вёрстки или различается сам поток: идентификатор говорит, где кнопка, но не сколько шагов до неё и чего ждать после. Пока реализации для версии нет, фабрика не падает, а пропускает тест с причиной: сценарий из нескольких страниц ждёт последнюю из них, а в JSON-отчёте у такого теста `status: 'skipped'` и аннотация `skip` с этим текстом (измерено прогоном). Расходящийся сценарий отсекается явно и в самом тесте: `test.skip(appVersion === 'legacy', 'Legacy has no draft autosave')` — причина попадает в отчёт (по документации, <https://playwright.dev/docs/test-annotations>), а page object о различиях версий не знает. Гостевые сценарии выключают авторизацию через `test.use({ storageState: { cookies: [], origins: [] } })` на уровне файла и выделяются в отдельный проект по маске `testMatch`, когда таких файлов становится больше трёх.

### 1.2 Контракт локаторов

Реестр `TEST_IDS` в `libs/test-ids` — объект `as const` с именами по домену: `TEST_IDS.editor.publish`. Его импортируют оба приложения и тесты, поэтому идентификатор существует в одном месте. В Angular реестр защищает компиляция: атрибутивная директива `[cmsTestId]` принимает вход типа `TestId`, выведенного из реестра, и переименование в реестре роняет сборку приложения на каждом устаревшем шаблоне. В AngularJS шаблоны не компилируются, поэтому гарантия другая: директива `test-id` бросает исключение на неизвестном идентификаторе в dev-сборке, а задача CI сверяет литералы `test-id="…"` в шаблонах с реестром. На время миграции атрибуты двух версий могут различаться: `use.testIdAttribute` принимает список через запятую, `'data-testid,data-qa'`, и `getByTestId` находит элемент по любому из них (описание опции — <https://playwright.dev/docs/api/class-testoptions#test-options-test-id-attribute>).

### 1.3 Приоритет локаторов

Порядок один для обеих реализаций: `getByRole` с доступным именем; затем `getByLabel` и `getByPlaceholder` для полей; `getByTestId` — для контейнеров и неинтерактивных блоков, у которых роли нет. Запрещены классы вёрстки и любые следы фреймворка: классы `ng-binding` и `ng-scope` AngularJS добавляет только при включённой отладочной информации `$compileProvider.debugInfoEnabled` (по исходникам AngularJS, файл `compile.js` модуля `ng`), а атрибуты директив вроде `ng-model` исчезают вместе с миграцией. Запрет закреплён линтером: правило `playwright/no-raw-locators` из `eslint-plugin-playwright` (по README пакета 2.11.0) не пропускает `page.locator('.btn')` в код page objects.

### 1.4 Требования командам фронтенда обеих версий

1. **Идентификатор из реестра на каждом интерактивном и бизнес-значимом элементе.** Критерий: сборка красная без идентификатора — в Angular через правило линтера на парсере `@angular-eslint/template-parser`, в AngularJS через проверку в CI из 1.2. Для AngularJS охват уже: версия уходит, поэтому идентификаторы ставятся в потоках с наибольшим трафиком, где их ждут тесты, а не на каждом элементе. Требование стоит первым, потому что его отсутствие дороже всего: в демо-приложении Conduit, на котором построен каркас этого репозитория, идентификаторов нет, и контейнеры ищутся по классам вёрстки из шаблонов спецификации RealWorld — `.error-messages`, `.tag-list`, `.sidebar`, `.banner`, `.article-content`, `.col-md-12`, `.feed-toggle`, `.nav-link.active` (по документации спецификации); такой локатор держится только на том, что шаблоны спецификации не меняются.
2. **Именование по домену, а не по вёрстке**: `article.publish`, не `btn-primary-2`. Критерий: тип `TestId` в реестре — шаблонный литерал `` `${Page}.${string}` ``, где `Page` — объединение имён страниц; ключ вне этой формы не компилируется.
3. **Семантическая разметка**: у каждого контрола роль и доступное имя — `<button>`, `<label for>`, `aria-label` там, где видимого текста нет. Критерий: в Angular правила доступности `@angular-eslint/eslint-plugin-template` — `label-has-associated-control`, `elements-content` (по списку правил плагина), для обеих версий проверка `@axe-core/playwright` в CI (по документации, <https://playwright.dev/docs/accessibility-testing>); в итоге `getByRole` находит элемент без CSS, и смена тега-обёртки или класса тест не трогает.
4. **Идентификатор и доступное имя — публичный контракт.** Их удаление или переименование — ломающее изменение. Критерий: `CODEOWNERS` на `libs/test-ids` требует ревью команды автотестов.
5. **Детерминированные состояния загрузки и ошибок.** Критерий: у каждого асинхронного блока есть конечное состояние с идентификатором (`feed.loaded`, `feed.error`), по которому тест ждёт web-first ассертом.
6. **Никаких сгенерированных идентификаторов** вроде `item-4f2a`. Критерий: проверка в CI из 1.2 не пропускает литерал, которого нет в реестре.

## 2. Оптимизация жизненного цикла конфигурации

### 2.1 Матрица проектов из переменных окружения

Списки сред, версий приложения и браузеров приходят переменными `ENVS`, `APP_VERSIONS`, `BROWSERS` через запятую; их разбирает zod-схема модуля окружения с дефолтами `dev`, `next`, `chromium`, так что без единой переменной конфиг даёт одну комбинацию. Массив `projects` в `defineConfig<TestArgs, WorkerArgs>` (второй типовой параметр делает `appVersion` в `use` проверяемым компилятором; по типам 1.62.1) строится `flatMap` по трём спискам; setup-проект среды и её браузерные проекты разведены по `testDir`, и браузерные зависят от setup-проекта:

```ts
const projects = env.ENVS.flatMap((envName) => [
  { name: `check:${envName}`, testDir: 'tests/setup', use: { baseURL: URLS[envName] } },
  ...env.APP_VERSIONS.flatMap((appVersion) =>
    env.BROWSERS.map((browser) => ({
      name: `${envName}:${appVersion}:${browser}`,
      testDir: 'tests/ui',
      dependencies: [`check:${envName}`],
      use: {
        ...devices[DEVICES[browser]],
        baseURL: URLS[envName],
        appVersion,
        testIdAttribute: appVersion === 'legacy' ? 'data-testid,data-qa' : 'data-testid',
      },
    })),
  ),
]);
```

Так `ENVS=dev,stage APP_VERSIONS=legacy,next BROWSERS=chromium,webkit` даёт два setup-проекта и восемь браузерных, а `--project=stage:next:chromium` запускает одну комбинацию вместе с её setup-проектом (по документации, <https://playwright.dev/docs/test-projects>).

### 2.2 CI против локальной отладки

Переключатель — `process.env.CI`; GitHub Actions выставляет её сам (по документации GitHub). В CI стенд либо отвечает, либо нет, и ждать нечего: `use.actionTimeout` и `use.navigationTimeout` по 10 с, `expect.timeout` 5 с, `timeout` 30 с, `maxFailures: 10`, `forbidOnly: true`, `globalTimeout` 15 мин; к этому зависимость от setup-проекта из 2.3 — упавший бэкенд даёт красный прогон за секунды с адресом и кодом ответа в отчёте. `retries: 0` на гейте внутренней среды: повтор маскирует нестабильный тест. Каркас этого репозитория ходит на общий публичный стенд, поэтому в его `playwright.config.ts` один повтор в CI оставлен против сетевых сбоев стенда; нестабильность повтор не прячет — тест, прошедший со второй попытки, отчёт помечает как `flaky` (по документации, <https://playwright.dev/docs/test-retries>).

Локально флаг `--debug` уже разворачивается в `PWDEBUG=1` с нулевым таймаутом, одним воркером и видимым браузером (по исходникам пакета `playwright` 1.62.1, `lib/program.js`, и по документации, <https://playwright.dev/docs/debug>), дублировать это в конфиге не нужно. Дыра в другом: `--ui` переменную `PWDEBUG` не выставляет (по исходникам `cli/testActions.js` 1.62.1) и setup-проекты сам не запускает (по документации, <https://playwright.dev/docs/test-ui-mode>). Её закрывает собственная переменная `PW_LOCAL_DEBUG=1`: при ней `timeout: 0`, `expect.timeout: 0`, `actionTimeout: 0`, `workers: 1`, `trace: 'on'` — на точке останова можно сидеть сколько нужно, и трейс остаётся.

### 2.3 Ловушка конфигурации: где валидировать секреты

Механизм — зависимости проектов (`dependencies`), а не `globalSetup`. `globalSetup` выполняется в процессе раннера без фикстур, без трейса и без записи в отчёте (по документации, <https://playwright.dev/docs/test-global-setup-teardown>), поэтому падение на отсутствующем пароле админки останется строкой в консоли CI без артефактов. Setup-проект — обычный тест: у него есть `request`, трейс и запись в отчёте, а при его падении зависимые проекты не стартуют вовсе и в сводке прогона значатся как `did not run`.

Сам `playwright.config.ts` не проверяет ни сеть, ни секреты. Он вычисляется в процессе раннера, при `--list` и в UI-режиме, а затем заново в каждом воркере: воркер импортирует файл конфига сам (по исходникам пакета `playwright` 1.62.1, `lib/common/index.js`); исключение на отсутствующем секрете сломало бы даже перечисление тестов и проекты, которым секрет не нужен. Поэтому схема окружения объявляет секреты необязательными, `ADMIN_PASSWORD: z.string().optional()`, а обязательными их делает setup-проект той среды, где они нужны:

```ts
test('Check the stage secrets and the backend', async ({ request }) => {
  expect(env.ADMIN_PASSWORD, 'ADMIN_PASSWORD is required for stage').toBeDefined();
  const response = await request.get('/api/health');
  expect(response.status(), `GET ${response.url()} responded ${response.status()}`).toBe(200);
});
```

Единственное, что роняет конфиг, — нарушенная форма матрицы: неизвестный браузер или пустой список сред падают до перечисления тестов с именем переменной в тексте ошибки. `globalSetup` остаётся для локальной уборки без сети. Так сделано в каркасе этого репозитория: `src/config/env.ts` разбирает схему при импорте и бросает только на некорректном значении; `tests/setup/env.setup.ts` делает один GET и падает с адресом и кодом ответа; в `playwright.config.ts` проект `chromium` объявляет `dependencies: ['setup']`, а `globalSetup` лишь чистит `allure-results`.

## 3. Внедрение

Всё в этом разделе — о монорепозитории CMS, не об этом репозитории. Порядок: сначала `libs/test-ids`, затем реализации `pages/next/` по потокам с наибольшим трафиком — публикация, редактирование, комментарии. Каталог `pages/components/` появляется с первым компонентом, который ищет элементы только по реестру и ролям и потому работает в обеих версиях одной реализацией; до принятия реестра фронтендом такого кода нет. Правило «новые тесты только через `pages/contract/`» закрепляется линтером: `no-restricted-imports` запрещает файлам из `tests/**` импортировать `pages/legacy/**` и `pages/next/**`. Шаблоны page object и спеки лежат в `apps/cms-e2e/templates/`, чек-лист код-ревью тестов — в шаблоне pull request репозитория. Проект `cms-e2e` связан с обоими приложениями через `implicitDependencies` в `project.json`, цели `e2e` и `e2e-ci` выводит плагин `@nx/playwright/plugin`, и `nx affected -t e2e` в CI запускает его при изменении любого из приложений (по документации Nx, <https://nx.dev/docs/technologies/test-tools/playwright/introduction>). От бэкенда нужен API тестовых данных: `POST /test-data` создаёт набор под идентификатор прогона, `DELETE /test-data/{runId}` убирает его в teardown, и тест не готовит данные через UI. Метрика миграции считается из JSON-отчёта (`reporter: 'json'`) по полям `projectName` и `status` каждого теста (по типам репортера 1.62.1): доля сценариев со статусом `expected` в проектах обеих версий; цель — все совпадающие сценарии, а каждый расходящийся помечен `test.skip` с причиной. Очередь переноса страниц читается из того же отчёта: аннотации `skip` с текстом `No next implementation for …` показывают, какой реализации ждёт больше всего сценариев.
