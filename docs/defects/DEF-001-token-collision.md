# DEF-001. Одновременные регистрации получают один и тот же токен

| | |
| --- | --- |
| **Компонент** | демо-бэкенд Conduit, авторизация. `https://api.realworld.show/api`, исходники `realworld_dummy_server.py` репозитория `c4ffein/realworld-demo-deploy`, коммит `ba2b78f6` |
| **Обнаружен** | 2026-09-03 на прототипе авторизации, до первого коммита этого репозитория |
| **Воспроизведён** | 2026-09-09, вывод ниже |
| **Серьёзность** | высокая: ломает параллельный прогон, а класс дефекта — предсказуемый идентификатор сессии — в продуктовой системе означает доступ к чужой учётной записи |
| **Статус** | открыт, обход применён в каркасе |

## Что происходит

Регистрации, попавшие в одно значение целой секунды, получают **байт в байт
одинаковый токен**. Стенд привязывает его к сессии того, кто зарегистрировался
последним, и остальные аккаунты молча работают под чужой личностью: регистрация
отвечает 201, `GET /user` — 200, просто другим пользователем.

Для автотестов это худший вид дефекта: падает не авторизация, а произвольная
проверка ниже по сценарию, с сообщением вида «элемент не найден». *Следствие,
не измерено:* уборка данных идёт от имени токена, поэтому при коллизии один
воркер удаляет статьи другого.

## Воспроизведение

```bash
node docs/defects/def-001-repro.mjs
```

Зависимостей нет, нужен только Node 20 или новее. Скрипт делает два замера по
четыре регистрации — параллельно и с паузой в секунду, — затем спрашивает
`GET /user`, кому принадлежит каждый токен. Сверка идёт после того, как секунда
регистрации закончилась по часам стенда (секунда берётся из заголовка `Date`,
ожидание до `секунда + 2`): пока эта секунда идёт, привязку может перехватить
следующая регистрация, и ответ `OK` ничего не доказывал бы.

Код выхода: 0 — коллизии нет, **1 — дефект воспроизведён**, 2 — замер не
состоялся (неожиданный ответ стенда или неверные аргументы). Токены в выводе
маскированы. Флаги `--api` и `--n` (2–4) необязательны.

## Фактический результат

Прогон 2026-09-09, код выхода 1:

```
burst: 4 registration(s) in parallel — the defect
POST /users -> 201 username=def00117889075492fd4n0 token=token_d978…0ac5 whoami=def00117889075492fd4n1 MISMATCH
POST /users -> 201 username=def00117889075492fd4n1 token=token_d978…0ac5 whoami=def00117889075492fd4n1 OK
POST /users -> 201 username=def00117889075492fd4n2 token=token_d978…0ac5 whoami=def00117889075492fd4n1 MISMATCH
POST /users -> 201 username=def00117889075492fd4n3 token=token_d978…0ac5 whoami=def00117889075492fd4n1 MISMATCH
unique tokens: 1 of 4
```

Четыре аккаунта, один токен, три работают под чужой личностью. Исход
недетерминирован: побеждает привязка, выполнившаяся последней. Масштаб тоже
плавает — залп на границе секунды частично уедет в следующую и получит там свои
токены.

## Ожидаемый результат

Каждая регистрация получает собственный токен. Это даёт второй замер того же
прогона:

```
spread: 4 registration(s) 1s apart — the workaround
POST /users -> 201 username=def00117889075523e1fn0 token=token_08f2…d835 whoami=def00117889075523e1fn0 OK
POST /users -> 201 username=def00117889075523e1fn1 token=token_3c3b…7333 whoami=def00117889075523e1fn1 OK
POST /users -> 201 username=def00117889075523e1fn2 token=token_20d0…b270 whoami=def00117889075523e1fn2 OK
POST /users -> 201 username=def00117889075523e1fn3 token=token_a4db…b28f whoami=def00117889075523e1fn3 OK
unique tokens: 4 of 4
```

`MISMATCH` возможен и здесь: стенд общий, и в ту же секунду может
зарегистрироваться посторонний. Это не опровергает обход, а показывает ту же
причину с внешним участником.

## Причина

*По исходникам, не измерено.* Токен — чистая функция от идентификатора
пользователя и целой секунды, без случайной части (`generate_token`,
строки 1378–1381):

```python
payload = f"{user_id}:{int(time.time())}"
return f"token_{hashlib.sha256(payload.encode()).hexdigest()[:32]}"
```

Оба слагаемых у независимых регистраций совпадают: секунда — потому что запросы
пришли одновременно, идентификатор — потому что счётчик раздаёт номера по
порядку внутри сессии (строка 414), а свежая сессия всегда начинается с четырёх
демонстрационных пользователей. Затем `bind_jwt_to_session_id` удаляет прежние
привязки того же токена и записывает свою (строки 947–964, удаление на 956) —
побеждает последний.

Адрес источника в формулу не входит, `generate_token` его не принимает. Значит
регистрация постороннего клиента в ту же секунду перепривяжет наш токен к своей
сессии, и разводить по времени только собственные запросы недостаточно.

## Обход в каркасе

1. **Убрать одновременность.** Регистрации воркеров вынесены в setup-проект
   (`tests/setup/worker-sessions.setup.ts`) и идут одна за другой до старта
   браузерных тестов.
2. **Развести по секундам тех, кто регистрируется во время тестов.** Запасной
   путь через `src/fixtures/auth.fixture.ts` ждёт секунду, остаток которой от
   деления на число воркеров равен номеру слота.
3. **Не доверять коду 201.** `src/auth/worker-session.ts` сверяет личность через
   `GET /user` после конца секунды регистрации по часам стенда; несовпадение —
   повторная регистрация, до трёх попыток. Цена — около двух секунд на слот,
   один раз за прогон.

Первые две меры закрывают участников своего прогона; против чужой регистрации
работает только третья — она превращает такой случай в явное падение с текстом
`token collision on the stand` вместо загадочного «элемент не найден». Дефект
ловят тест `the header shows the worker user without the login form`
(`tests/ui/auth/worker-session.spec.ts`) и сверка формы настроек в сценарии
регистрации.

## Рекомендация владельцу стенда

Добавить в токен случайную часть, чтобы он перестал быть чистой функцией от
идентификатора и секунды. Это устраняет причину целиком.
