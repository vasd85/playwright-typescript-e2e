# Архитектура e2e-тестов для миграции CMS с AngularJS на Angular в Nx

Решение кейса: как организовать тесты и page objects, чтобы переход со старого фронтенда на новый не переписывал текст тест-кейсов, и как устроить жизненный цикл `playwright.config.ts`. Каркас в этом репозитории закреплён на `@playwright/test` 1.62.1; у фактов о стенде и об инструментах, взятых не из прогона, статус источника стоит рядом.

## 1. Управление изменениями в дизайне страниц

### 1.1 Абстракция тестов от реализации элементов

Предлагаемая раскладка проекта `apps/cms-e2e` в монорепозитории (не этот репозиторий):

```
apps/cms-e2e/
  tests/             сценарии на языке бизнеса, без локаторов
  pages/contract/    интерфейсы страниц и компонентов
  pages/legacy/      реализации для AngularJS
  pages/next/        реализации для Angular
  pages/components/  общие компоненты: шапка, список ошибок формы
  fixtures/          сборка: авторизация, API, фабрика страниц
  data/              builders тестовых данных
libs/test-ids/       реестр идентификаторов, общий для приложений и тестов
```

Тест знает только интерфейс: `await editor.publish(article)`, `await editor.expectError('title', "can't be blank")`. Локаторы живут в реализациях, а какая из них подставится, решает опция проекта `appVersion`: она объявлена через `test.extend` с `{ option: true, scope: 'worker' }` (по документации, <https://playwright.dev/docs/test-parameterize>) и задаётся в `use` каждого проекта конфига. Фабрика в фикстуре читает опцию и создаёт реализацию:

```ts
export interface EditorPage {
  open(): Promise<void>;
  publish(article: ArticleDraft): Promise<void>;
  expectError(field: 'title' | 'body', text: string): Promise<void>;
}

export const test = base.extend<{ editor: EditorPage }, { appVersion: AppVersion }>({
  appVersion: ['next', { option: true, scope: 'worker' }],
  editor: async ({ page, appVersion }, use) => {
    await use(appVersion === 'legacy' ? new LegacyEditorPage(page) : new NextEditorPage(page));
  },
});
```

Совпадающие 80 % сценариев идут в проектах обеих версий без единой правки текста теста. Расходящийся сценарий отсекается явно и в самом тесте: `test.skip(appVersion === 'legacy', 'Legacy has no draft autosave')` — причина попадает в отчёт (по документации, <https://playwright.dev/docs/test-annotations>), а page object о различиях версий не знает. Гостевые сценарии выключают авторизацию через `test.use({ storageState: { cookies: [], origins: [] } })` на уровне файла и выделяются в отдельный проект по маске `testMatch`, когда таких файлов становится больше трёх.

### 1.2 Контракт локаторов

Реестр `TEST_IDS` в `libs/test-ids` — объект `as const` с именами по домену: `TEST_IDS.editor.publish`. Его импортируют оба приложения и тесты, поэтому идентификатор существует в одном месте. В Angular реестр защищает компиляция: атрибутивная директива `[cmsTestId]` принимает вход типа `TestId`, выведенного из реестра, и переименование в реестре роняет сборку приложения на каждом устаревшем шаблоне. В AngularJS шаблоны не компилируются, поэтому гарантия другая: директива `test-id` бросает исключение на неизвестном идентификаторе в dev-сборке, а задача CI сверяет литералы `test-id="…"` в шаблонах с реестром. На время миграции атрибуты двух версий могут различаться: `use.testIdAttribute` принимает список через запятую, `'data-testid,data-qa'`, и `getByTestId` находит элемент по любому из них (измерено прогоном; описание опции — <https://playwright.dev/docs/api/class-testoptions#test-options-test-id-attribute>).

### 1.3 Приоритет локаторов

Порядок один для обеих реализаций: `getByRole` с доступным именем; затем `getByLabel` и `getByPlaceholder` для полей; `getByTestId` — для контейнеров и неинтерактивных блоков, у которых роли нет. Запрещены классы вёрстки и любые следы фреймворка: классы `ng-binding` и `ng-scope` AngularJS добавляет только при включённой отладочной информации `$compileProvider.debugInfoEnabled` (по исходникам AngularJS, файл `compile.js` модуля `ng`), а атрибуты директив вроде `ng-model` исчезают вместе с миграцией. Запрет закреплён линтером: правило `playwright/no-raw-locators` из `eslint-plugin-playwright` (по README пакета 2.11.0) не пропускает `page.locator('.btn')` в код page objects.

### 1.4 Требования командам фронтенда обеих версий

1. **Идентификатор из реестра на каждом интерактивном и бизнес-значимом элементе.** Критерий: сборка красная без идентификатора — в Angular через правило линтера на парсере `@angular-eslint/template-parser` (готового правила в `@angular-eslint/eslint-plugin-template` нет, по списку правил плагина), в AngularJS через проверку в CI из 1.2. Требование стоит первым, потому что его отсутствие дороже всего: в демо-приложении Conduit, на котором построен каркас этого репозитория, идентификаторов нет, и контейнеры ищутся по классам вёрстки из шаблонов спецификации RealWorld — `.error-messages`, `.tag-list`, `.sidebar`, `.banner`, `.article-content`, `.col-md-12`, `.feed-toggle`, `.nav-link` (по документации спецификации); такой локатор держится только на том, что шаблоны спецификации не меняются.
2. **Именование по домену, а не по вёрстке**: `article.publish`, не `btn-primary-2`. Критерий: тип `TestId` в реестре — шаблонный литерал `` `${Page}.${string}` ``, где `Page` — объединение имён страниц; ключ вне этой формы не компилируется.
3. **Семантическая разметка**: у каждого контрола роль и доступное имя — `<button>`, `<label for>`, `aria-label` там, где видимого текста нет. Критерий: в Angular правила доступности `@angular-eslint/eslint-plugin-template` — `label-has-associated-control`, `elements-content` (по списку правил плагина), для обеих версий проверка `@axe-core/playwright` в CI (по документации, <https://playwright.dev/docs/accessibility-testing>); в итоге `getByRole` находит элемент без CSS, и смена тега-обёртки или класса тест не трогает.
4. **Идентификатор и доступное имя — публичный контракт.** Их удаление или переименование — ломающее изменение. Критерий: `CODEOWNERS` на `libs/test-ids` требует ревью команды автотестов.
5. **Детерминированные состояния загрузки и ошибок.** Критерий: у каждого асинхронного блока есть конечное состояние с идентификатором (`feed.loaded`, `feed.error`), по которому тест ждёт web-first ассертом.
6. **Никаких сгенерированных идентификаторов** вроде `item-4f2a`. Критерий: проверка в CI из 1.2 не пропускает литерал, которого нет в реестре.

## 3. Внедрение

Всё в этом разделе — о монорепозитории CMS, не об этом репозитории. Порядок: сначала `libs/test-ids` и `pages/components/`, затем реализации `pages/next/` по потокам с наибольшим трафиком — публикация, редактирование, комментарии. Правило «новые тесты только через `pages/contract/`» закрепляется линтером: `no-restricted-imports` запрещает файлам из `tests/**` импортировать `pages/legacy/**` и `pages/next/**`. Шаблоны page object и спеки лежат в `apps/cms-e2e/templates/`, чек-лист код-ревью тестов — в шаблоне pull request репозитория. Проект `cms-e2e` связан с обоими приложениями через `implicitDependencies` в `project.json`, цели `e2e` и `e2e-ci` выводит плагин `@nx/playwright/plugin`, и `nx affected -t e2e` в CI запускает его при изменении любого из приложений (по документации Nx, <https://nx.dev/docs/technologies/test-tools/playwright/introduction>). От бэкенда нужен API тестовых данных: `POST /test-data` создаёт набор под идентификатор прогона, `DELETE /test-data/{runId}` убирает его в teardown, и тест не готовит данные через UI. Метрика миграции считается из JSON-отчёта (`reporter: 'json'`) по полям `projectName` и `status` каждого теста (по типам репортера 1.62.1): доля сценариев со статусом `expected` в проектах обеих версий; цель — все совпадающие сценарии, а каждый расходящийся помечен `test.skip` с причиной.
