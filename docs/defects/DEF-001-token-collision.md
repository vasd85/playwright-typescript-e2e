# DEF-001. Одновременные регистрации получают один и тот же токен

| | |
| --- | --- |
| **Идентификатор** | DEF-001 |
| **Компонент** | демо-бэкенд Conduit, авторизация |
| **Среда** | `https://api.realworld.show/api`; бэкенд `realworld_dummy_server.py` репозитория `c4ffein/realworld-demo-deploy`, коммит `ba2b78f6` |
| **Обнаружен** | 2026-09-03, при разработке фикстуры авторизации |
| **Воспроизведён** | 2026-09-09, вывод ниже |
| **Серьёзность** | высокая |
| **Статус** | открыт, обход применён в каркасе тестов |

## Описание

Две и более регистрации, попавшие в одно и то же значение целой секунды,
получают **байт в байт одинаковый токен**. Стенд привязывает этот токен к сессии
того, кто зарегистрировался последним, поэтому остальные аккаунты молча начинают
работать под чужой личностью. Никакой ошибки при этом нет: все регистрации
возвращают 201, а `GET /user` отвечает 200 — просто другим пользователем.

## Влияние

Дефект ломает любой параллельный прогон автотестов. Наблюдалось: воркеры
получали общий токен, и тест падал на проверке шапки — в браузере был
пользователь другого воркера. Диагностируется тяжело, потому что симптом не
похож на причину: падает не авторизация, а произвольная проверка ниже по
сценарию, с сообщением вида «элемент не найден». *Следствие, не измерено:*
уборка данных идёт от имени токена, поэтому при коллизии один воркер удаляет
статьи другого.

**Почему этот класс дефектов критичен там, где идут платежи.** Оценка
серьёзности выше дана для демонстрационного стенда. Но сам класс —
предсказуемый идентификатор сессии, выведенный из данных, совпадающих у разных
пользователей, — в платёжном продукте означает доступ к чужой сессии, то есть к
чужим данным и операциям. Это нарушение изоляции пользователей, а не дефект
удобства: частота проявления на приоритет не влияет.

## Шаги воспроизведения

1. Отправить четыре запроса `POST /users` параллельно, так чтобы они пришлись на
   одну целую секунду по часам сервера. Заголовок авторизации не ставится:
   регистрация с чужим токеном ломает этот токен.
2. Дождаться ответов. Все четыре возвращают 201 и токен.
3. Для каждого выданного токена выполнить `GET /user` с заголовком
   `Authorization: Token <токен>`.
4. Сравнить имя из ответа с именем, под которым регистрировались.

Скрипт, делающий ровно это, лежит рядом и не требует ни установки зависимостей,
ни запуска тестов:

```bash
node docs/defects/def-001-repro.mjs
```

Он выполняет два замера: четыре параллельные регистрации и четыре с паузой в
секунду. Коды выхода:

| Код | Значение |
| --- | --- |
| 0 | все личности сошлись, коллизия не воспроизвелась |
| 1 | **дефект воспроизведён** — хотя бы один токен резолвится в чужого пользователя |
| 2 | замер не состоялся: стенд ответил не 201 на регистрацию, не 200 на `GET /user` или не ответил вовсе |

Код 1 означает найденный дефект, а не поломку скрипта. Токены в выводе
маскированы.

## Фактический результат

Прогон 2026-09-09, код выхода 1:

```
stand: https://api.realworld.show/api

burst: 4 registration(s) in parallel — the defect
POST /users -> 201 username=def00117889066339133n0 token=token_8622…27ac whoami=def00117889066339133n1 MISMATCH
POST /users -> 201 username=def00117889066339133n1 token=token_8622…27ac whoami=def00117889066339133n1 OK
POST /users -> 201 username=def00117889066339133n2 token=token_8622…27ac whoami=def00117889066339133n1 MISMATCH
POST /users -> 201 username=def00117889066339133n3 token=token_8622…27ac whoami=def00117889066339133n1 MISMATCH
unique tokens: 1 of 4
```

Четыре разных аккаунта получили один токен, и он принадлежит второму из них —
три из четырёх работают под чужой личностью.

Исход коллизии непредсказуем: побеждает привязка, выполнившаяся последней, а
порядок завершения параллельных запросов не задан. Число совпавших токенов тоже
плавает — залп на границе секунды частично уедет в следующую (2026-09-07 при тех
же четырёх регистрациях уникальных токенов было два). Предсказуема сама
коллизия, а не её исход.

## Ожидаемый результат

Каждая регистрация получает собственный токен, и каждый токен резолвится в того
пользователя, которому выдан. Именно это даёт второй замер того же прогона, где
регистрации разведены на секунду:

```
spread: 4 registration(s) 1s apart — the workaround
POST /users -> 201 username=def001178890663469cbn0 token=token_70bd…f578 whoami=def001178890663469cbn0 OK
POST /users -> 201 username=def001178890663469cbn1 token=token_f6b7…3a5e whoami=def001178890663469cbn1 OK
POST /users -> 201 username=def001178890663469cbn2 token=token_01fd…a55c whoami=def001178890663469cbn2 OK
POST /users -> 201 username=def001178890663469cbn3 token=token_5bdb…b87f whoami=def001178890663469cbn3 OK
unique tokens: 4 of 4
```

Во втором замере тоже возможен `MISMATCH` — стенд общий, и в ту же секунду может
зарегистрироваться кто-то посторонний. Это не опровергает обход, а показывает ту
же причину с внешним участником.

## Анализ причины

*Статус источника: по исходникам, не измерено.* Файл `realworld_dummy_server.py`,
коммит `ba2b78f6`.

Токен — чистая функция от идентификатора пользователя и целой секунды, без
случайной части (строки 1378–1381):

```python
payload = f"{user_id}:{int(time.time())}"
return f"token_{hashlib.sha256(payload.encode()).hexdigest()[:32]}"
```

Оба слагаемых у независимых регистраций совпадают. Секунда — потому что запросы
пришли одновременно. Идентификатор — потому что счётчик объектов раздаёт номера
по порядку внутри сессии (строка 414), а свежая сессия всегда начинается с
четырёх демонстрационных пользователей, так что первый зарегистрированный в ней
получает один и тот же `id`.

Дальше обработчик регистрации привязывает выданный токен к сессии запроса
(строка 1560), а `bind_jwt_to_session_id` перед этим удаляет все прежние
привязки того же токена (строки 947–964, удаление на строке 956). Побеждает
последняя регистрация — её сессия и станет владельцем общего токена.

Отсюда же следует, что **дефект не ограничен одним клиентом**: адрес источника в
формулу токена не входит — `generate_token` его вообще не принимает. Любая
анонимная регистрация постороннего клиента, попавшая в ту же секунду, получит тот
же токен и перепривяжет его к своей сессии. Разводить по времени собственные
запросы поэтому недостаточно. *(Такой случай наблюдался при разработке фикстуры:
в браузере оказался пользователь, которого этот прогон не создавал. Артефакт того
прогона в репозиторий не входит, поэтому здесь он приведён как иллюстрация к
разбору исходников, а не как доказательство.)*

## Обход, применённый в каркасе

Две меры, обе в `src/auth/worker-session.ts`.

**Первая — убрать одновременность.** Регистрации воркеров вынесены из времени
тестов в setup-проект (`tests/setup/worker-sessions.setup.ts`) и идут
последовательно, по одной на слот.

**Вторая — не доверять коду 201, а спросить, кому принадлежит токен.** После
регистрации выполняется `GET /user`, и его ответ годен только тогда, когда
секунда регистрации закончилась **по часам стенда**: секунда берётся из заголовка
`Date` ответа на регистрацию, сверка ждёт `Date` не меньше этой секунды плюс две
(одна — чтобы секунда токена истекла, вторая — запас на кеш заголовка `Date` у
сервера). После этой границы токен уже никем не может быть сгенерирован заново, и
привязка окончательна. Несовпадение — повторная регистрация в новой секунде, до
трёх попыток. Цена — около двух секунд на слот, один раз за прогон: стартовая
пауза 1,5 секунды плюс ожидание границы; измеренные секунды регистраций четырёх
слотов идут через одну — `S`, `S+2`, `S+4`, `S+6`.

Первая мера закрывает столкновения внутри своего прогона. Против чужой
регистрации на общем стенде работает только вторая: она превращает такой случай
в явное падение с понятным текстом вместо загадочного «элемент не найден».

## Чем дефект ловится в наборе тестов

- Тест `the header shows the worker user without the login form`
  (`tests/ui/auth/worker-session.spec.ts`) — шапка обязана показывать
  пользователя своего воркера.
- Сценарий регистрации (`tests/ui/auth/registration.spec.ts`) сверяет форму
  настроек с именем и почтой: эти данные приходят от сервера, поэтому подмена
  личности видна, даже если шапка отрисована по локальному ответу.
- При исчерпании трёх попыток регистрация падает с текстом
  `token collision on the stand`, то есть причина названа прямо.

## Рекомендация владельцу стенда

Добавить в токен случайную часть, чтобы он перестал быть чистой функцией от
идентификатора и секунды. Это устраняет причину целиком; проверки на стороне
клиента остаются полезными, но перестают быть обязательными.
